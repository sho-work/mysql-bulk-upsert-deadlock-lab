## 結論

**電話番号がワーカー間で重ならないBulk Upsertでも、RRでPRIMARYのsupremumを介した循環待機を再現した。** 既存のみ（B2）と既存・新規混在（B3）で各3回発生し、RCでは同じ条件の100試行中0回だった。

B2/B3の全6件のデッドロックログで、両トランザクションのPRIMARY supremumに対するX保持とinsert intention待機が記録された。添付図の機構を、追加のSELECT FOR UPDATEを含まないBulk Upsertで確認できた。

本番DDLとAuroraバージョン、当時のログは未照合。これは本番に近い仮構成で同じ仕組みを再現した結果であり、本番の原因の確定ではない。

## 実行条件

- MySQL Community 8.0.40 / InnoDB / innodb_autoinc_lock_mode=2
- Ruby 3.3.6 / ActiveRecord 7.1.5 / activerecord-import 1.8.1 / mysql2 0.5.6
- AUTO_INCREMENTのBIGINT主キーと、電話番号文字列のセカンダリUNIQUE索引
- JSON histories / created_at / updated_at
- 2ワーカー、各10行、100試行。各試行はTRUNCATEと初期データ復元
- ワーカーごとに独立接続、開始ゲートで同時実行。スケジューリング自体は非決定的
- import!の更新対象はhistories / updated_at。自動リトライなし

## 結果表

「デッドロック試行数」は100回のうち1213が発生した試行数。「失敗トランザクション数」もこの実行では同数。各ケースは200トランザクション。

| ケース | 条件 | RR：デッドロック試行数 | RC：デッドロック試行数 |
|---|---|---:|---:|
| B1 | 異なるキー・新規のみ | 0 / 100 | 0 / 100 |
| B2 | 異なるキー・既存のみ | 3 / 100 | 0 / 100 |
| B3 | 異なるキー・既存→新規の混在 | 3 / 100 | 0 / 100 |
| B4 | 同じキー・同じ順序 | 0 / 100 | 0 / 100 |
| B5 | 同じキー・逆順 | 1 / 100 | 90 / 100 |

タイムアウト1205・その他のワーカーエラーは0。全ワーカーが成功した試行で、キー集合・JSON履歴・created_at・updated_atのDB結果を検証し、全件合格した。失敗を含む試行の最終状態は同じ検証の対象にしていない。

RCでもB5では同じレコードへの逆順更新がデッドロックを起こした。代表ログはセカンダリUNIQUE上のenc_shared_00000005 / 00000006を互いに待つ状態を示す。RCがすべてのデッドロックを防ぐという結果ではない。B5のRRの1件はPRIMARY supremumの循環待機だった。

発生頻度はこの1回の実行での値。分離レベル全般の優劣や確率を、この値だけから一般化しない。

## B3の直接証拠

代表：trial-39、trx 8016 / 8015。

| トランザクション | 保持 | 要求して待機 |
|---|---|---|
| 8016 | PRIMARY、space 246 / page 4 / heap 1、supremum、X | 同じsupremum、X insert intention waiting |
| 8015 | PRIMARY、space 246 / page 4 / heap 1、supremum、X | 同じsupremum、X insert intention waiting |

各ワーカーの入力電話番号はenc_w0_*とenc_w1_*に分かれており、全100試行で交差がないことを入力ログで確認した。SQLはid=NULLでのINSERT ... ON DUPLICATE KEY UPDATEである。

**既存行のみのB2でも再現した**点に注意する。アプリの意図が「既存更新だけ」であっても、SQLはINSERTを試みてキー重複時に更新へ進む。ギャップロックを取得する正確な内部コード経路はこの実験では解析していない。

## 図の補助実験C

id=13926を1件だけ登録。A/Bで、存在しないid=13927をSELECT FOR UPDATEし、続いてAが13927、Bが13928をINSERTした。

- RR：両trxのPRIMARY supremum XがGRANTED。AのX,INSERT_INTENTIONがWAITINGとなり、data_lock_waitsでA→Bを確認。Bの挿入で1213。ログに循環待機。
- RC：検索後に観測されたロックはテーブルIXのみ。両INSERTが完了。
- A/Bは最後にROLLBACKし、2件のINSERTによる変更を破棄した。初期データ1件は次のケースのTRUNCATEでリセットする。
- 初回の範囲検索版は2つ目のSELECTが1205になったため、ギャップだけを狙う存在しない主キーの完全一致検索に修正した。

この補助実験には添付コードにないロック読み取りがある。B2/B3の再現とは別に扱う。

## 保存した証拠と再実行

[証拠ディレクトリ](../../evidence/run-38278254695/)には、集計JSON、環境情報、補助実験のreport.json、B2/B3/B5の代表デッドロックログを保存。

全149ファイルの生ログはActionsのdeadlock-experiment-results artifactに保存（保持期限は7日）。代表ログと集計はリポジトリ内に保存し、artifact失効後も参照できる。

```bash
docker compose build
docker compose up -d --wait db
CASE=B3 WORKERS=2 BATCH_SIZE=10 TRIALS=100 ISOLATION=repeatable_read docker compose run --rm runner
CASE=B3 WORKERS=2 BATCH_SIZE=10 TRIALS=100 ISOLATION=read_committed docker compose run --rm runner
ISOLATION=repeatable_read docker compose run --rm runner bundle exec ruby controlled_gap.rb
ISOLATION=read_committed docker compose run --rm runner bundle exec ruby controlled_gap.rb
docker compose logs --no-color db > results/mysql-error.log
```

ケースBはタイミング依存のため、同じ回数や頻度での発生は保証しない。ケースCはロック取得順を制御する。
